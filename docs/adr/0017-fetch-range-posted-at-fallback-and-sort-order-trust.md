# Fetch Range: undated offers filter as "now"; pagination trusts newest-first order

US34 introduces `fetch_range` (a per-Source `since`/`until` window on `posted_at`) inside the shared `run_paginated_ingestion`. Two sub-decisions came up while designing the filter itself:

**Undated offers.** When a mapped offer's `posted_at` can't be parsed (missing, or a malformed value from the source), the filter treats it as if `posted_at` were `datetime.now(UTC)` at the moment that offer is being processed — evaluated fresh per offer, not once per run, since a rate-limited paginated run can span a long time. This value is used only for the range comparison; it is never written back into the persisted `Offer.posted_at` column, which stays `None` when the source gave nothing — `posted_at` is a fact about the source's claim, and fabricating one would misrepresent it (the real scrape time is already recorded via `Offer.created_at`). We considered unconditionally keeping undated offers regardless of the range (simpler, but silently ignores an explicit `until` upper bound and needed a separate special case to keep such offers from wrongly tripping the early-stop below); treating them as "now" satisfies both `since` and `until` correctly with one mechanism, and happens to also resolve the early-stop case below for free — an offer with no determinable date is never "before since," so it never counts towards a page looking exhausted.

**Pagination early-stop.** Once every offer on a page is confirmed older than `since`, pagination stops (further pages can only be older still) — this assumes the connector's feed is sorted newest-first, true for all three connectors today. We decided to trust this assumption without a runtime guard (e.g. asserting the max `posted_at` seen is non-increasing) rather than add defensive bookkeeping for a scenario that requires an external source API change to trigger. If a connector's sort order ever changes, this optimization would silently truncate ingestion — a future investigator debugging "why are offers missing" for a specific connector should check this assumption first.
