# Content-based duplicate detection is a second, independent mechanism, not a replacement for dedup_hash

`persist_offer` already deduplicates on `dedup_hash`: a SHA-256 of the normalized canonical URL, falling back to a hash of `title|company|location` when there's no comparable URL. That catches re-ingesting the *same posting from the same source*, but misses the case that's grown more likely as connectors have multiplied (9 registered, six added in one recent batch): the same job reposted on a *different* job board under a *different* URL. US48 adds `_find_content_duplicate`, a plain `SELECT` run before the existing hash/insert logic, matching on `company` + `title` + the `salary_min`/`salary_max`/`salary_currency` triple. It is global — not scoped to a Source or connector — because catching a cross-connector repost is the point.

This is deliberately a second, independent check rather than a change to `compute_dedup_hash`'s fallback. The two can disagree by design: a repost with a slightly different location string but an identical salary is caught by the new check and missed by the old fallback; conversely a repost with identical location but a shifted salary figure is caught by the fallback and missed by the new check. Merging them into one hash would force a single normalization strategy on two conceptually different signals (URL/location identity vs. compensation identity) for no real gain — both independently return `(existing_row, created=False)` on a hit, and if both would match the same incoming offer it is still only skipped once, since `persist_offer` short-circuits on the first hit.

Exact-equality was chosen over overlap/tolerance matching for the salary triple. A tolerance band (e.g. "within 10%") would need a threshold with no natural default, and would risk merging two genuinely different offers that happen to share a company and a generic title (e.g. two distinct "Backend Engineer" roles at "Acme" with unrelated salary bands). Exact equality is simple, has no tunable to get wrong, and only ever collapses postings that already look identical. It also directly implies: two offers with the same numeric salary but different currency (PLN vs USD) never match, since no FX conversion is performed — currency mismatch is a hard signal that these are not necessarily the same market rate for the same role. The nullable columns need `IS NOT DISTINCT FROM` rather than `=`, since ordinary SQL equality never matches `NULL = NULL` and a posting with no listed salary should still dedupe against another posting with no listed salary.

Company/title normalization (case folding, legal-suffix stripping) was explicitly deferred. `"Acme"` and `"ACME"`, or `"Acme Sp. z o.o."` and `"Acme"`, are not treated as duplicates in this pass — a real but smaller-scope problem than the cross-connector-repost scenario this story targets, left for a future pass if it proves to matter in practice.

No DB-level uniqueness constraint backs this check. A standard Postgres unique index treats every `NULL` as distinct from every other `NULL` — the opposite of what "both salary fields absent counts as a match" requires — and a partial or expression index encoding `IS NOT DISTINCT FROM` semantics is more complexity than a first pass warrants. The accepted cost is a narrow race window: two concurrent `persist_offer` calls for the same content-duplicate can both pass the pre-check and both insert, leaving two rows until the next ingestion run's check (or a manual cleanup) collapses them. This mirrors the project's already-accepted stance on concurrent `/ingest` triggers (see `docs/architecture/ingestion.md`): no lock, and dedup still prevents most duplicate rows, so the cost of a race is wasted work, not silent data corruption.

Finally, a skipped content-duplicate is only logged (INFO, naming company/title/salary and the matched row's id) — no new field on `IngestionResult`, `IngestResponse`, `ManualRunResponse`, or `SourceStatus`, and no frontend change. Surfacing a count end-to-end was considered and declined for v1, consistent with this project's preference for minimal, bare-numeric UI additions over speculative visibility that has no consumer yet.
