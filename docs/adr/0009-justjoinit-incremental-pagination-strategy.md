# JustJoin.it: early-stop pagination on already-seen offers, not a fixed page cap — and why NoFluffJobs gets no equivalent fix

Both connectors capped fetches at a fixed page/item count and re-fetched from page 1 on every run (`ARCHITECTURE.md`'s own JustJoin.it and NoFluffJobs sections called this out as deferred work). Fixing it required live-verifying two things about JustJoin.it's endpoint that weren't previously confirmed, and concluding that NoFluffJobs cannot be fixed the same way.

**JustJoin.it's cursor pagination has a hard, exact ceiling, and its own "next page" hint lies about it.** Probing live confirmed `from + itemsCount > 10000` always returns a bare `500`, regardless of `itemsCount` (tested at 50 and 100) — `meta.totalItems: 10000` is a real enforced cap, not an estimate. Worse, `meta.next.cursor` does not go `null` before this boundary: at `from=9900`, the response's `next.cursor` is `10000`, but requesting `from=10000` guarantees a `500`. The connector's existing "stop gracefully, keep what was fetched, if a page fetch fails after the first page succeeded" behavior (`app/connectors/justjoinit.py`) is what actually absorbs this — it was not written with this boundary in mind, but happens to handle it correctly, so it was left unchanged.

**The feed is confirmed newest-first**, which is what makes an early-stop-on-already-seen strategy sound rather than a coincidence. Fetching `from=0,10,20` (30 offers) live showed `publishedAt` strictly non-increasing across every item. Without this, "N consecutive already-seen `dedup_hash`es" wouldn't reliably mean "we've caught up" — it could just be a coincidental cluster in an unordered feed, and stopping there would silently skip newer offers further in (the exact bug being fixed, just relocated).

Given both facts, `run_justjoinit_ingestion` now interleaves fetch and persist per page (rather than accumulating all pages then persisting once at the end), and stops fetching further pages once 20 consecutive offers come back as `created=False` from `persist_offer`'s own `ON CONFLICT DO NOTHING` result — no separate `SELECT dedup_hash IN (...)` pre-check, since the insert's return value already carries that information for free. `max_pages` stays as a hard safety ceiling, raised from 5 to 100 (`100 × page_size 100 = 10,000`, matching the confirmed real limit exactly, not a guess) for the case of a cold/empty `Source` where nothing is ever already-seen.

**NoFluffJobs gets `Source.last_fetched_at` for staleness visibility only — no fetch-side change.** The endpoint is a re-ranked "recommended offers" feed (`page` was already confirmed not to behave as an offset), not a stable chronological list. A client-side filter that skips persisting offers with `posted_at` older than the last successful run — as originally proposed — would risk silently and permanently losing an offer that re-enters the feed's ranking later without ever having been ingested before, since nothing would ever retry it. That's a real, if narrow, silent-data-loss risk for a saving that's marginal anyway (`ON CONFLICT DO NOTHING` already makes re-persisting an already-seen offer cheap). True incremental fetch for NoFluffJobs remains blocked on the `search/posting` endpoint fix noted in `docs/adr/0004-nofluffjobs-json-endpoint-investigation.md`.

**`Source.last_fetched_at` is set by both trigger paths, `/scheduler/run/{source}` and `/ingest/{source}`, even though only the former writes a `scheduler_runs` row** (ADR 0006). Browser-based verification of the new Offers-page source-status widget caught this the hard way: the widget's timestamp didn't move after clicking "Fetch now" until `app/ingestion/service.py`'s `_trigger_ingest_async` was also updated to set `last_fetched_at` on success. ADR 0006's "not scheduler-audited" stance is about the run-history table, not this checkpoint — a job-seeker's on-demand fetch is exactly the kind of success `last_fetched_at` needs to reflect.
