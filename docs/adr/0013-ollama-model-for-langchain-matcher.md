# Ollama model for the LangChain Matcher: `llama3.1:8b`, VRAM ceiling unchanged despite batch tolerance

US22's Matcher chain needs a local Ollama model that scores a structured `Offer` against the active `Profile` across six weighted dimensions and produces a `MatchScore` via `.with_structured_output()`. OD-2 originally named `Llama 3.3 70B` / `Qwen 2.5 32B` / `Mistral 24B` as candidates "sized for Phase 3's Matcher, assuming whatever VRAM is available." ADR 0011 resolved the model question for CV extraction only, deliberately deferring the Matcher's own choice — noting that the Matcher's latency budget (batch scoring, not a synchronous request) differs enough from CV extraction's that it deserved its own look at the time. This ADR is that look, and resolves OD-2 for the LangChain Matcher specifically.

**Batch tolerance does not raise the VRAM ceiling.** The instinct that a looser latency budget might unlock one of OD-2's larger candidates does not hold: Ollama still has to load the full model into this machine's 8GB VRAM (RTX 3070 Laptop, per ADR 0011) regardless of whether the caller can tolerate a slower response. A 24B+ model still needs ~14GB+ even at 4-bit quantization, so it still spills to CPU/system RAM — the failure mode ADR 0011 ruled out is about memory footprint, not response-time patience. Batch scoring makes a slow model *tolerable*, but it doesn't make a too-big model *fit*. The 7-8B-class ceiling from ADR 0011 therefore applies unchanged here.

**Within that ceiling, this task is not purely an instruction-following problem the way CV extraction was.** CV extraction's deciding factor was instruction-adherence (extract facts only, never embellish) — an axis where `llama3.1:8b` clearly leads `qwen2.5:7b` (IFEval). The Matcher's dimension scoring (`skill_match`, `seniority_fit`, etc.) is closer to a judgment/fit-assessment task, which leans nearer the knowledge-heavy axis where `qwen2.5:7b` was noted to have an edge (MMLU-Pro, GPQA). This is a real distinction from CV extraction's reasoning, not a repeat of it.

**`llama3.1:8b` is still the pick**, because the Matcher also has a hard instruction-adherence requirement of its own — respecting the fixed dimension weights, staying within the `[0,1]` per-dimension range, and correctly applying the deal-breaker-cap and missing-field-conservatism rules the prompt asks for — and getting that instruction-following right matters more here than a marginal edge on fit-judgment quality, especially since the deal-breaker cap and conservative-scoring fallback are enforced in code (not left to the model) as a deterministic backstop regardless of which model is chosen. Introducing a second model would also compete for the same 8GB of VRAM with no demonstrated quality gap large enough to justify it. `qwen2.5:7b` remains the documented fallback if real scoring runs later show weight/format drift.

The model name is set via `MATCHER_OLLAMA_MODEL` (`app/config.py`'s new `Settings.matcher_ollama_model`, independent of `Settings.ollama_model`), so revisiting this choice — including trying `qwen2.5:7b` for its fit-judgment edge — is a config change, not a code change.
