# The Protocol: stock Playwright cannot maintain access past Cloudflare's Managed Challenge — spike fails, story stops at Phase 1

Background research documented that every plain-HTTP path into theprotocol.it (homepage, a guessed `/api/offers`, the robots.txt-listed sitemap) returns `403` with a `cf-mitigated: challenge` header — Cloudflare's Managed Challenge. Phase 1's job was not to re-confirm that (already known going in) but to answer a narrower question: can a *browser-driving* client — stock Playwright Chromium, no third-party stealth or CAPTCHA-solving service — clear the challenge and reach real page content, reliably enough to power a connector that fetches multiple pages per run?

**Method.** A throwaway script (`playwright.async_api`, not committed) launched Chromium headless, navigated to `https://theprotocol.it/` with a realistic desktop `User-Agent` and `pl-PL` locale, and inspected the response status, `cf-mitigated` header, page title, and rendered body text for challenge markers (`Just a moment`, `cf-mitigated`, etc.) versus real content (job-category listings, a non-empty body). `playwright install chromium` was run once as a one-time local setup step per the story's own instructions.

**First result: pass.** The very first navigation in the session returned `200`, no `cf-mitigated` header, title `"Praca w branży IT - theprotocol.it"`, and a real rendered body (`body_text_len=5517`) containing genuine site content — specialization/technology filter labels (`backend`, `frontend`, `QA/testing`, `devOps`, ...) and search UI, not a challenge shell. This alone would satisfy a literal one-shot reading of the story's "Playwright clears the Cloudflare challenge" test row.

**Every subsequent result: persistent fail.** All later navigations in the same investigation — spread across several minutes of normal interactive tool-call pacing, not a rapid bot-speed burst — returned `403` with `cf-mitigated: challenge`, page title `"Just a moment..."`, and an empty rendered body. This was not a transient blip: it was reproduced identically across four separate attempts, using both a fresh browser launch each time and, separately, a single long-lived page waiting 5-8 seconds in place on the challenge screen in case it was a self-resolving JS challenge (it was not — the title and empty body were unchanged after the wait). No cookies, wait strategy, or retry cleared it once triggered.

Headed mode (the story's fallback if headless is blocked) could not be evaluated: `chromium.launch(headless=False)` hung and then failed trying to reach this sandbox's `DISPLAY`/D-Bus session (`Failed to connect to the bus: ... /run/dbus/system_bus_socket: No such file or directory`), an environment limitation of this sandbox rather than a signal about Cloudflare — consistent with `docs/adr/0003-justjoinit-json-endpoint-investigation.md` and `docs/adr/0004-nofluffjobs-json-endpoint-investigation.md`'s own note that a working headless-Chromium network capture was not available in this environment. Headed was not reachable to test at all, so it cannot be reported as a fallback that works.

Screenshot capture also failed independently of the challenge (`Page.screenshot` timed out waiting on font loading even for a trivial `about:blank` + static-HTML page in this sandbox), so no image evidence was captured; this is a rendering-pipeline limitation of the sandbox, not related to Cloudflare, and does not affect the status/header/title/body-text evidence above, which is conclusive on its own.

**What this means for feasibility.** The pattern observed — one clean pass, then a hard, non-self-clearing Managed Challenge on every following request regardless of pacing — reads as Cloudflare escalating its classification of this client (likely on repeat-visit/automation fingerprinting signals inherent to a stock headless Chromium session: `navigator.webdriver`, CDP-protocol tells, or similar) rather than a simple request-rate throttle a `rate_limit_delay_seconds` could work around. A connector needs sustained, repeated fetches across a run (multiple listing/detail pages), not one lucky page load, so the single initial pass does not constitute feasibility. No third-party stealth or CAPTCHA-solving tooling was used at any point (out of scope per the story's Domain Decision), and per that same Domain Decision, using one to force a pass would count as a fail for this story's purposes regardless — moot here, since none was needed to get the first pass and none was tried afterward.

**Go/no-go: no-go.** Per the story's Phase 1 decision point, this story stops here. `app/connectors/`, `app/ingestion/normalize.py`, and `app/ingestion/registry.py` are untouched. The `playwright` dev dependency added for this spike was reverted (`uv remove --group dev playwright`); `pyproject.toml` and `uv.lock` are unchanged from before this story. The throwaway spike script was not committed.

**Revisit conditions**, per the story's own stopping guidance: if theprotocol.it's Cloudflare edge configuration changes (e.g. the Managed Challenge is relaxed or scoped differently), or a legitimate API access path becomes available (an official/partner API, or a JSON endpoint reachable without a browser at all — not investigated here since the story's own Background section already ruled out the plain-HTTP paths), this spike should be re-run with the same method: a single fresh Playwright navigation first, then repeated navigations over realistic elapsed time, checking for the same `cf-mitigated`/title/body markers documented here.
