# Pracuj.pl: stock Playwright clears Cloudflare cleanly across repeated navigations — spike passes, Phase 2 proceeds

P3US41's Background section noted Pracuj.pl (operated by Grupa Pracuj, the same company behind theprotocol.it) returns `403` with `cf-mitigated: challenge` on every plain-HTTP content path (homepage, a guessed API endpoint, every robots.txt-listed sitemap URL) — the same Cloudflare Managed Challenge blocker `docs/adr/0024-the-protocol-playwright-cloudflare-feasibility-spike.md` characterized for The Protocol. Phase 1's job was to answer the same narrow question ADR 0024 asked, independently: can stock Playwright Chromium — no stealth plugin, no proxy rotation, no CAPTCHA-solving service — clear the challenge and reach real page content reliably enough to power a connector that fetches multiple pages per run, given that Pracuj.pl and The Protocol are separate properties that may carry different WAF tuning despite the shared operator?

**Method.** Mirrored ADR 0024 exactly: a throwaway script (`scripts/_pracuj_spike.py`, `playwright.async_api`, not committed) launched Chromium headless, navigated to `https://www.pracuj.pl/` with a realistic desktop `User-Agent` and `pl-PL` locale, and inspected response status, the `cf-mitigated` header, page title, and rendered body text for challenge markers (`Just a moment`, `cf-mitigated`, `Enable JavaScript and cookies`) versus real content. Unlike ADR 0024's single investigation session, this spike ran **five separate fresh-browser-launch navigations spread across ~3.5 minutes** (2026-07-14 15:34:57 → 15:38:11) before drawing any conclusion, precisely because ADR 0024 found a single lucky first pass insufficient evidence — Cloudflare escalated its classification of that client after one pass. `playwright install chromium` required no `--with-deps`/sudo step here; a Chromium build was already present in `~/.cache/ms-playwright/`.

This environment differs from the US39 sandbox in one relevant way — a `DISPLAY` (WSLg, `192.168.178.159:0.0`) and a working `dbus-launch` were available — so headed mode, which ADR 0024 explicitly left untested, was also attempted here per the story's instruction to check rather than assume.

**Result: pass, all five headless attempts.** Every one of the five navigations returned `200`, no `cf-mitigated` header, page title `"Pracuj.pl - Praca - Strona główna"`, and a real rendered body (`body_len` 7006–7010 across attempts) containing genuine site content — navigation labels (`Oferty pracy`, `Profile pracodawców`, `Moje konto`), the live offer-count string (`"0 ofert pracy od najlepszych pracodawców"` — a template artifact of the fixture-free live page, not a real zero), and category tabs (`Wszystkie`, `IT`, `Praca fizyczna`, `Sprzedaż`). No challenge markers appeared in any attempt. This is a materially different pattern from The Protocol's "one clean pass, then a hard non-self-clearing challenge on every later request" — Pracuj.pl showed no such escalation across the full ~3.5-minute window and five fresh browser launches.

**Headed mode: also pass, once given a real X server.** The first headed attempt, relying on WSLg's forwarded `DISPLAY`/D-Bus, failed — but with an environment error (`Missing X server or $DISPLAY`, `Failed to connect to socket /run/dbus/system_bus_socket`), not a Cloudflare signal: the sandboxed process could not actually reach a running X server through that forwarded display value. Since `Xvfb` was available locally, a second headed attempt ran under `xvfb-run -a` (a real local X server, not relying on WSLg forwarding) and passed cleanly: `200`, no `cf-mitigated` header, title `"Pracuj.pl - Praca - Strona główna"`, `body_len=6719`, real content. This closes the gap ADR 0024 left open (headed mode was reachable-but-untested there) with a clean result for this property.

**What this means for feasibility.** Five fresh-browser headless navigations across ~3.5 minutes, plus one Xvfb-backed headed navigation, all reached real content with no challenge, no escalation, and no `cf-mitigated` header at any point. This is a clean pass by the story's own bar ("real page content reached, not a challenge/CAPTCHA screen") and does not show the single-lucky-pass pattern ADR 0024 warned against — the repeated-attempt design that would have caught that pattern here did not surface it. Grupa Pracuj evidently tunes Cloudflare's Managed Challenge per-property rather than uniformly: Pracuj.pl's edge configuration is materially more permissive to a stock Playwright client than theprotocol.it's, confirming the story's own caution not to assume identical WAF behavior across the two properties.

**Go/no-go: go.** Phase 2 proceeds. The `playwright` dev dependency added for this spike is retained (not reverted, unlike ADR 0024). The throwaway spike script (`scripts/_pracuj_spike.py`) is not committed; its extraction logic was homepage-only (status/title/body-text checks) and does not yet cover offer-listing or offer-detail structured extraction — that extraction work happens fresh in Phase 2 implementation, informed by this spike's confirmation that the browser session itself is viable, not by any parsing logic from this throwaway script.

**Revisit conditions.** If Pracuj.pl's Cloudflare edge configuration is later tightened (e.g. `cf-mitigated: challenge` starts appearing, matching theprotocol.it's behavior), or the connector implemented in Phase 2 starts hitting challenge pages mid-run in production, re-run this spike's method — five-plus fresh-browser navigations spread over several minutes — before assuming a config or rate-limiting fix will resolve it, per ADR 0024's own finding that pacing alone does not clear an escalated challenge classification.
