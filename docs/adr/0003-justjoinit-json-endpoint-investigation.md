# JustJoin.it: a real, unauthenticated JSON endpoint exists, but not at any of its plausible-looking URLs

US12 needed to resolve OD-4 for JustJoin.it: does a JSON endpoint exist behind the SPA, or does ingestion require a Playwright scraper? A local headless-Chromium network capture (the natural first choice, mirroring "open a browser's devtools Network tab") stalled and never completed in this sandboxed environment, so the investigation was done by downloading `justjoin.it`'s own served Next.js JS bundles and grepping them for the real API client code, then confirming every candidate against the live site with `curl`.

The obvious guesses were all wrong. `https://api.justjoin.it/offers` — the subdomain named directly in the page's own runtime config as `baseApiUrl` — returns `404 Invalid endpoint`; that Rails-style backend does not serve the public offer list at that path. `https://profile.justjoin.it/offers` — guessed from the config's `baseCpUrl` — redirects (307) to a login page; that subdomain is the authenticated candidate-profile web app, not a raw API host. The bundle code that actually powers the public `/job-offers` listing page calls `candidateGateway.offers.getByCursor()`, whose axios instance is configured with `baseURL: () => isomorphicConfig.getCandidateProfileApiUrl()`, which resolves to `cpApiUrl` in the page's embedded runtime config — and that value is not an absolute URL at all, but the *relative* path `/api/candidate-api`, proxied through justjoin.it's own Next.js server. The real, live, working, unauthenticated endpoint is:

```
GET https://justjoin.it/api/candidate-api/offers?from=<cursor>&itemsCount=<page size>
```

Confirmed live: `curl -A "recruFlow/0.1" "https://justjoin.it/api/candidate-api/offers?from=0&itemsCount=5"` returns `200` with real current offers, no cookies or auth required, and our own `recruFlow/0.1` User-Agent is not blocked by Cloudflare. The response is `{"data": [...offer objects...], "meta": {"from", "totalItems", "prev": {"cursor", "itemsCount"}, "next": {"cursor", "itemsCount"}}}` — cursor-paginated, `meta.next.cursor` is `null` at the end of a page window. `meta.totalItems` was observed as a flat `10000` regardless of actual result count (almost certainly a capped/estimated figure, not a literal count), and requesting a very deep cursor (`from=9999`) returned a bare `500` — the API is not perfectly robust deep into its own pagination, which is why `app/connectors/justjoinit.py` bounds pagination via a configurable `max_pages` rather than looping until `meta.next.cursor` is `null`.

We chose to verify every candidate URL against the live system rather than trust the config keys' names at face value (`baseApiUrl`/`baseCpUrl` look authoritative but are not what the offers list actually uses), the same discipline `docs/adr/0002-sjctl-contract-verified-against-live-binary.md` established for sjctl. If JustJoin.it changes this endpoint or its response shape, `_fetch_justjoinit_json`, `_extract_offer_list`, and `map_justjoinit_offer` in `app/connectors/justjoinit.py` are the places to re-verify — the JS-bundle-grepping method documented here (download the site's own `/_next/static/chunks/*.js`, grep for the offers gateway) is the fastest way to re-confirm without a working headless browser.
