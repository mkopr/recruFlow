# NoFluffJobs: a real, unauthenticated JSON endpoint exists, but it is a capped feed, not a true paginated catalog

Resolving the NoFluffJobs half of OD-4 (the JustJoin.it half was already resolved — see `docs/adr/0003-justjoinit-json-endpoint-investigation.md`, whose discipline this investigation reused) required answering: does NoFluffJobs expose a JSON endpoint behind its Angular SPA, or does ingestion require a Playwright scraper? As with JustJoin.it, a local headless-Chromium network capture was not attempted (previously observed to stall in this sandboxed environment); instead `https://nofluffjobs.com`'s own served Angular bundle (`main.<hash>.js`, downloaded directly with `curl`) was grepped for API client code, and every candidate was confirmed against the live site with `curl` before being trusted.

The bundle contains a `HttpClient`-based gateway with roughly a dozen `/api/*` paths. Two looked like plausible listing endpoints and were both wrong guesses in different ways: `POST /api/search/posting` — the endpoint backing the real search-results page, built via `prepareSearchParams()` and a `criteriaSearch`-shaped body — requires `salaryCurrency`/`salaryPeriod` query params (confirmed via its own `400` error messages naming them) but then returns a bare `500 Internal server error` for every body shape tried (an empty object, and the full `criteriaSearch` skeleton — all-empty-arrays — copied verbatim from another endpoint's own response shape). It was not pursued further since a second, simpler candidate already worked. `GET /api/posting` (no `search`) does return `200`, but with no pagination controls at all — it dumps NoFluffJobs's entire current listing inventory as a single ~89 MB JSON response, unusable as a per-run ingestion call.

The endpoint actually used is the one backing the site's homepage "recommended offers" feed:

```
GET https://nofluffjobs.com/api/joboffers/main?pageSize=<N>&salaryCurrency=PLN&salaryPeriod=month
```

Confirmed live: `curl -A "recruFlow/0.1" "https://nofluffjobs.com/api/joboffers/main?pageSize=20&salaryCurrency=PLN&salaryPeriod=month"` returns `200` with real current offers, no cookies or auth required. `salaryCurrency` and `salaryPeriod` are hard requirements — omitting either produces a `400` naming the missing parameter. `page` is accepted but was verified to **not** behave as an offset: requests for `page=1`, `page=2`, `page=3`, `page=5`, `page=10`, `page=50`, `page=100`, and `page=300` (all with `pageSize=20`) returned byte-identical (or near-identical, modulo a couple of pinned/sponsored postings at the front) result sets — this is a "recommended for you" style aggregate feed, not an offset-paginated listing. `pageSize`, on the other hand, does scale the number of postings returned, but non-linearly and by more than the requested count (`pageSize=20` → 140 postings, `pageSize=100` → 327, `pageSize=500` → 2043), consistent with the endpoint internally querying multiple categories/segments and concatenating them rather than slicing one ordered list.

Because of this, `app/connectors/nofluffjobs.py` does **not** implement a page-fetch loop the way `justjoinit.py` does. It issues exactly one `GET` per ingestion run, with `pageSize` set from the Source's `config_json` (`page_size`, default `100`). Looping over `page` values would not surface additional offers (verified above), and there is no cursor or "next page" field in the response to loop on safely. This is a documented known limitation: this connector surfaces a bounded, recommendation-ranked slice of NoFluffJobs's current listings (observed up to ~2000 postings at `page_size=500`), not the full ~12,000-offer catalog reachable only via the broken `search/posting` endpoint or the unusably large `/api/posting` dump. Because ingestion is a single HTTP request per run, no `rate_limit_delay_seconds` config key was added — there is nothing to delay between.

The response envelope is `{"postings": [...], "totalCount": <int>, "totalPages": <int>, "criteriaSearch": {...filter facets...}, ...}`. Each posting object has (among other fields) `id` (a mixed-case, location-suffixed slug unique per listing, e.g. `"senior-java-developer-itfs-Warszawa-13"`), `url` (the lowercase version of `id`, confirmed live as the path segment of a working job page: `GET https://nofluffjobs.com/job/<url>` returns `200`), `name` (company name — not `company`), `title`, `location.places[].city` (list, joined the same way `map_justjoinit_offer` joins `locations[].city`), `location.fullyRemote` (boolean — the authoritative "no on-site presence required" signal; the top-level `fullyRemote` field on the posting itself was observed to always be `False` across a ~2000-record sample and is not used), `seniority` (a list, observed always length 1 in sampling but handled defensively), `salary.{from,to,currency,type}` (`type` takes values `permanent`/`b2b`/`zlecenie` in the wild — passed through as `contract_type` verbatim, no vocabulary translation, matching the `Remote`/`Contract Type` glossary rule that cross-source unification must follow), `posted` (a Unix **milliseconds** epoch integer, not an ISO string — divided by 1000 and converted with `datetime.fromtimestamp(..., tz=UTC)`), and `reference` (a code shared across the several location-duplicate posting entries NoFluffJobs generates for one underlying job ad — not used as `external_id` since it is not unique per listing; `id` is used instead). The listing payload has no full job-description field, so `description` is always mapped to `None`, the same documented limitation `map_justjoinit_offer` has.

If NoFluffJobs changes this endpoint or its response shape, `_fetch_nofluffjobs_json`, `_extract_offer_list`, and `map_nofluffjobs_offer` in `app/connectors/nofluffjobs.py` are the places to re-verify — re-download the site's current `main.<hash>.js` bundle (linked from `https://nofluffjobs.com/`'s own HTML `<script src>` tags) and grep for `/api/joboffers/main` or its neighbours under the same Angular `HttpClient` gateway class.
