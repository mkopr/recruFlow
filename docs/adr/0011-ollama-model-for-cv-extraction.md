# Ollama model for CV extraction: `llama3.1:8b`, chosen for this machine's 8GB VRAM budget

US19's extraction chain needs a local Ollama model that turns CV text into structured `Profile` fields (skills, roles, education, certifications, languages) and is trustworthy enough to honor a hard "facts only, nothing inferred or embellished" constraint. OD-2 (`user stories/000 high level guide.md`) named `Llama 3.3 70B` / `Qwen 2.5 32B` / `Mistral 24B` as candidates, but those were sized for Phase 3's Matcher, deferred to P3US2, and assumed "whatever VRAM is available." This story resolves the model question for the extraction chain specifically, against this development machine's actual hardware.

**This machine's real headroom rules out the OD-2 candidates entirely.** The dev box has a single NVIDIA GeForce RTX 3070 Laptop GPU with 8GB VRAM (`nvidia-smi`), plus 15GB RAM (WSL2). Even at aggressive 4-bit quantization, a 24B model needs ~14GB, a 32B model ~19GB, and a 70B model ~40GB — all far past 8GB. Running any of them would mean spilling most layers to CPU/system RAM, which on a laptop iGPU-adjacent setup turns a synchronous `POST /profile/upload` request (the user is waiting on the response, not polling a batch job) into a multi-minute wait. That rules out the OD-2 shortlist outright for this endpoint, independent of extraction quality.

**Candidates sized for 8GB VRAM: `llama3.1:8b` vs `qwen2.5:7b`.** Both quantize (Q4_K_M) to roughly 4.7-4.9GB, comfortably inside 8GB with headroom for KV-cache/context on a CV-length input (a CV is a few thousand tokens at most). Mistral 7B v0.3 and Gemma2 9B were also considered and are viable on paper, but neither has a clear edge over the two front-runners for this task and both have a smaller LangChain/Ollama community footprint, so they weren't pursued further. Polish-language support (relevant for Phase 1/3's Polish job market) was initially weighed since Qwen2.5 documents broader multilingual coverage than Llama 3.1's eight officially-tuned languages — but it turned out to be moot: CVs handled by this story are in English, so multilingual strength isn't a deciding factor here.

**`llama3.1:8b` wins on the property that matters most for this chain: instruction-following fidelity.** The acceptance criteria's hard constraint — extract facts only, never infer or embellish — is fundamentally an instruction-adherence problem, not a knowledge or coding problem. Llama 3.1 8B Instruct leads Qwen2.5 7B Instruct on IFEval (strict instruction-following) and is generally regarded as the safer choice when a pipeline demands strict schema/instruction compliance, while Qwen2.5 7B's edge shows up on knowledge- and code-heavy benchmarks (MMLU-Pro, HumanEval, GPQA) that aren't what this chain does. Both models work fine with Ollama's structured-output mode (JSON-schema-constrained decoding) and LangChain's `ChatOllama.with_structured_output`, so tooling maturity isn't a differentiator. `qwen2.5:7b` is the documented fallback if real CV extractions later show `llama3.1:8b` under-extracting or mis-structuring fields.

The model name is set via `OLLAMA_MODEL` (`app/config.py`'s existing `Settings.ollama_model`), not hardcoded in the extraction chain, so swapping to `qwen2.5:7b` or revisiting this choice later is a config change, not a code change. `.env.example`'s `OLLAMA_MODEL` is updated from the placeholder `llama3.3:70b` to `llama3.1:8b` to match. Phase 3's Matcher (OD-2) may reuse `llama3.1:8b` or pick its own model when P3US2 lands — the Matcher's latency budget (batch scoring, not a synchronous request) is different enough from this chain's that it deserves its own look at the time, on whatever hardware is available then.
