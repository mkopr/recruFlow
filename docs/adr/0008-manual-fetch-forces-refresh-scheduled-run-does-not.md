# Job-seeker's manual fetch uses force_refresh=True; every other trigger stays False

BUG01: the Offers page's "Fetch now" button always reported `Fetched 0, 0 new` for SOLID.Jobs. Root cause: `dispatch_ingestion` never threaded `force_refresh` through, so every caller ran `sjctl sync`, which is scoped to `sjctl watch add`-configured watches (see [ADR 0001](0001-solid-jobs-sync-vs-search-cache-strategy.md)) — and no watch has ever been created, so `sync` structurally has nothing to match and correctly returns zero results.

We now thread `force_refresh` through `DispatchFn`/`dispatch_ingestion`/`_dispatch_solid_jobs`, and only `POST /ingest/{source}` (the job-seeker-facing trigger behind "Fetch now", per [ADR 0006](0006-manual-ingest-trigger-is-not-scheduler-audited.md)) passes `force_refresh=True`, switching SOLID.Jobs to `sjctl search` against the Source's `config_json` filters against the live API. Both the automatic hourly run (`app/scheduler/service.py`) and the scheduler subsystem's own audited manual trigger (`POST /scheduler/run/{source}`, also documented in ADR 0006) keep `force_refresh=False` — despite the latter also being "manually" triggered, it exists to re-run the *scheduled* job on demand for ops/audit purposes, not to satisfy a job-seeker's "get me fresh results right now." Only `/ingest/{source}` maps to the "explicitly requested" re-fetch that ADR 0001 already carves out.

This means the two "manual" triggers in the system now behave differently from each other for SOLID.Jobs specifically — a future reader should not assume "manual" is a single concept. If sync ever gains real watches (rejected as out of scope for this fix), this split should be revisited.
