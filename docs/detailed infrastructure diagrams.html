1 System context

recruFlow runs entirely on one developer machine via Docker Compose. There is no cloud deployment, no auth layer, and no multi-tenant concern; the diagram below is the whole system: a browser talking to a local API, a local Postgres, a local Ollama LLM runtime, and outbound calls to public job board sources. SMTP send (Phase 4) is drawn dashed because it is designed for but not built yet.

2 Docker Compose topology & startup gating

docker-compose.yml defines five services. Only one real startup dependency exists: api waits for db's healthcheck before it starts (condition: service_healthy); frontend, db_test, and ollama all start independently, with no depends_on edges at all. make up brings up all five together with hot reload for api and frontend.

app container Postgres container Ollama container depends_on / startup gate
Note: api does not wait on ollama at the container-orchestration level; there is no Compose depends_on between them. If Ollama is slow to warm up, the API still starts; the first CV-extraction or matcher call simply waits on Ollama's own readiness at request time.

3 Ingestion pipeline flow

Three independent triggers converge on one dispatch seam (CONNECTOR_REGISTRY), so adding a connector never touches the scheduler, the matcher, or the frontend. Every run ends at exactly one of two places: a persisted offers row, or a dead-letter row in ingestion_failures.

app / trigger pure dispatch / logic external call persisted table dead-letter table
Three orthogonal per-connector knobs, all stored inside Source.config_json (no schema migration per knob):
  • Fetch Range: the posted_at date window a run accepts (mode: "all" | "range", since/until).
  • Auto-Fetch: whether the connector's scheduled job runs at all (per-source on/off toggle).
  • Fetch Scope: all offers vs. filtered-by-hard-skills at fetch time; only SOLID.Jobs, Bulldogjob, and Pracuj.pl support it.

5 Scoring pipeline flow

A single backlog-draining job is the only automatic scorer; ingestion itself never triggers scoring (that coupling caused a measured ~43% duplicate-score rate and was removed). A module-level lock closes the remaining race between the backlog job and a manual POST /score/batch call.

6 Dead-letter queue & retry flow

Every handled, anticipated failure across ingestion and scoring lands in one of two dead-letter tables through a single write primitive, and is retried through one generic registry-driven read/retry API rather than four bespoke ones.

7 Database schema

Nine tables total: six v1 domain tables, scheduler_runs (the ingestion audit trail), and two dead-letter tables. No ORM relationship() is used anywhere; every join in application code is an explicit select(...).join(...). The diagram below draws only the primary column-aligned edges for clarity; every foreign key is still listed in full in each table's card underneath.

Full column reference

sources

  • id PK, autoincrement
  • name string(100), unique, not null; display-only, never used for dispatch
  • connector string(50), nullable; scheduler dispatch key
  • config_json JSONB: schedule, fetch_range, auto_fetch_enabled, fetch_scope
  • last_fetched_at timestamptz, nullable
  • created_at / updated_at

offers

  • id PK
  • dedup_hash string(64), unique + indexed
  • source_id, external_id, canonical_url (nullable), title, company, location, remote, seniority
  • salary_min / salary_max / salary_currency, contract_type, description, posted_at, industry_tags (JSONB)
  • applied / hide / notes / link_opened_at: user-owned, set only via PATCH
  • raw_payload JSONB; ELT raw response, always populated
FK → sources.id

profiles

  • id PK
  • name unique; internal bookkeeping key, not domain content
  • status (draft / active-ish string), is_active boolean
  • data JSONB: skills, roles, education, preferences, deal_breakers, Skill.hard flags

cv_versions

  • id PK
  • cv_markdown, cover_letter_markdown (nullable), tone (nullable)
  • status string, no DB enum
FK → offers.id, profiles.id

match_scores

  • id PK
  • engine (Literal langchain | sjctl; only langchain used)
  • score_percent int 0–100, not null
  • dimensions JSONB (open dict), rationale text
  • no uniqueness constraint on (offer_id, profile_id); re-scores always insert
FK → offers.id, profiles.id

applications

  • id PK
  • status: drafted · reviewed · sent · failed · interview · offer · rejected
  • send_method (nullable), error_message (nullable), sent_at (nullable)
  • no creation path yet; Phase 4 not built
FK → offers.id, profiles.id, cv_versions.id (nullable)

scheduler_runs

  • id PK
  • trigger_type: automatic | manual
  • status: running | ok | error
  • fetched_count / created_count (nullable Integer), warning (boolean)
  • started_at, finished_at (nullable while running)
FK → sources.id · index (source_id, started_at)

ingestion_failures

  • DeadLetterMixin: id, dedup_key (unique), failure_type, error_message, raw_payload (nullable JSONB)
  • status: open | resolved, occurred_at, resolved_at (nullable)
  • page (nullable)
FK → sources.id, scheduler_runs.id (nullable) · index (source_id, occurred_at)

scoring_failures

  • DeadLetterMixin fields (as above)
FK → offers.id, profiles.id · index (offer_id, occurred_at)

9 Frontend application map

Four routes under one react-router-dom shell (App.tsx). Every page follows the same page → component → hook → typed-API-wrapper layering.

  • /: OfferListPage Phase 1
    • OfferFilters, ScoreFilter, OfferTable, per-connector FetchNowButton
    • hooks: useOffers (fetch-on-filter, 300ms debounce, paginated), useOfferScoreDetail (on-demand drawer), useScoreAlerts (SSE)
    • consumes: GET /offers, GET /offers/{id}/score, POST /ingest/{source}, GET /scoring/events
  • /profile: ProfileEditorPage Phase 2
    • CvUploadControl, SkillsTable (hard-skill star toggle), RolesList, EducationList, CertificationsList, LanguagesList, DealBreakersList, PreferencesFields
    • hooks: useProfileEditor (localStorage-cached draft, save-never-activates by default)
    • consumes: GET /profile, PUT /profile, POST /profile/upload
  • /failures: FailuresPage hardening
    • FailureFilters (process-conditional), FailuresTable, FailureDetailDrawer
    • hooks: useFailures (mirrors useOffers, no debounce)
    • consumes: GET /failures/{process}, POST /failures/{process}/{id}/retry
  • /settings: SettingsPage
    • Fetch cadence (interval / Fetch Range / Auto-Fetch / Fetch Scope per connector), Notifications (score alert threshold, mute, test sound)
    • hooks: useConnectorSettings, useKnownSources, useOfferCleanup, useSchedulerStatus, useScoringStatus
    • consumes: GET /connectors, every PUT /scheduler/sources/* route, GET /scheduler/status, GET /scoring/status, GET /offers/cleanup-preview, DELETE /offers
Known gap: make test-frontend (vitest) runs but is deliberately not wired into make ci / GitHub Actions yet; see docs/adr/0007-vitest-introduced-but-not-wired-into-make-ci.md.

11 Configuration reference

Every setting is read once through app/config.py's Settings (pydantic-settings, .env-driven) and cached via @lru_cache. database_url, ollama_base_url, and ollama_model have no defaults; a process importing app.main without them raises immediately.
