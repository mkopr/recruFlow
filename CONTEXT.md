# recruFlow

Local job-application automation system. This file extends `CLAUDE.md`'s domain glossary table with terms resolved during design/grilling sessions — precise definitions and the alternatives deliberately rejected, not implementation detail.

## Language

**Dead Letter Queue** (ingestion/scoring):
A durable, queryable record of a pipeline failure that previously only produced a log line — one row per *resource* (a job posting for validation failures, a Source's ingestion for fetch failures, an offer×profile pair for scoring failures), not one row per occurrence. A resource's row is upserted in place on recurrence (keyed by `dedup_key`) and flipped to `status="resolved"` on a successful retry, rather than deleted or appended-to — see `docs/adr/0016-dead-letter-rows-are-mutable-per-resource-not-append-only.md`. The name is accurate (not just an audit log) because retry/requeue is a first-class operation: `POST /failures/{process}/{id}/retry` replays the resource's stored input (the raw payload, or the offer/profile pair) through the same code path that would have produced it originally.
_Avoid_: "failure log" or "audit log" (implies append-only, one row per occurrence — the opposite of how this behaves).

**Fetch Range**:
The `posted_at` window a Source's ingestion — automatic *and* manual runs alike — will accept, held in `config_json.fetch_range`. `mode: "range"` bounds it to `[since, until]` (either edge optional, both inclusive); `mode: "all"` disables the check entirely. An offer whose `posted_at` can't be determined (missing or unparseable) is filtered as if its date were "now," evaluated fresh per offer — never persisted as a fabricated `posted_at`, see `docs/adr/0017-fetch-range-posted-at-fallback-and-sort-order-trust.md`. Manual triggers (`/ingest/{source}`, `/scheduler/run/{source}`) respect Fetch Range exactly like the automatic job does — `force_refresh` is a separate, unrelated bypass (only of the already-seen pagination early-stop), see `docs/adr/0018-manual-triggers-respect-fetch-range.md`.
_Avoid_: assuming `force_refresh=True` means "ignore Fetch Range too" — it doesn't; the two are orthogonal.

**Auto-Fetch**:
Whether a Source's *automatically scheduled* job is allowed to run at all, held in `config_json.auto_fetch_enabled` (defaults to `true`). Turning it off pauses the live APScheduler job (`scheduler.pause_job`) rather than removing it — the job still exists, still shows up in status, and resumes on the next tick once re-enabled. Distinct from `trigger_type` (`"automatic"` vs `"manual"`, tracked per-run on `SchedulerRun`) — Auto-Fetch governs whether the automatic trigger_type ever fires; manual trigger paths are entirely unaffected either way.
_Avoid_: calling it a connector on/off switch — it doesn't disable the connector or block manual runs, only the scheduled cadence.

**Deal-Breaker Cap**:
The rule that any Profile deal-breaker matched in an Offer caps the Matcher's score_percent at 40, regardless of the weighted dimension total. Enforced in code after the LLM call (a deterministic backstop), never left to the LLM to self-apply — a future engine (or a prompt-only implementation) that skips this code-level check would be non-compliant even if the model's rationale mentions the deal-breaker. **Detection itself is also deterministic, never an LLM-judged field** — see `docs/adr/0014-deal-breaker-detection-deterministic-not-llm.md`: offer text is adversarial, so folding detection into the LLM's structured output would let a manipulated listing talk the model out of flagging a real deal-breaker. Matching is case-insensitive and tokenizes on hyphen/underscore/slash/whitespace, joining tokens with an *optional* separator (`"on-site"` / `"onsite"` / `"on site"` all match one pattern) while single-token deal-breakers keep plain word boundaries (so `"Java"` never matches inside `"JavaScript"`) — a deliberate recall-vs-security trade-off: paraphrased deal-breakers ("must work from the office" vs. a `"remote-only"` deal-breaker) are missed, in exchange for a guarantee that cannot be prompt-injected around.
_Avoid_: Red flag penalty (red flags are one of the six weighted dimensions at 5%; the deal-breaker cap is a separate, absolute override on top of the weighted total, not part of that dimension's score)

**Unopened Match Highlight** (offer list, P3US35):
The row-level visual indicator (reusing `.card-accent`) on the offer list marking an Offer as a strong, not-yet-looked-at match — true when `score_percent >= scoreAlertPrefs.minScorePercent && link_opened_at == null && canonical_url != null`. Always derived fresh from current data on every `GET /offers`, never stored or cached as its own column or "seen" flag — see `docs/adr/0019-offer-highlight-is-derived-not-stored.md`. `link_opened_at` (the underlying timestamp) is set exactly once, server-side, the first time `PATCH /offers/{offer_id}` receives `{"link_opened": true}`; it is a request flag, not a client-supplied timestamp, and repeat calls are a no-op.
_Avoid_: "seen" or "read" flag (implies a stored per-offer state the client toggles directly; the client only ever signals the click event via `link_opened`, it never writes the timestamp or the highlight itself)
